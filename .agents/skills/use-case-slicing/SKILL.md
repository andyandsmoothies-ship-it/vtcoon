# Use Case Slicing (AIUP Edition)

A skill for partitioning Use Cases into thin, vertical, test-protected slices based on **Use-Case 3.0 Principle 10 ("Build the system in slices")** and **Writing Use Cases for AI** (Martinelli, 2026).

A use-case slice is one or more paths through a use case, plus the design, code, and tests that implement and verify them. Slices—not full use cases—are the well-formed backlog items for agile delivery and AI code generation.

---

## The 6 Golden Rules of Slicing

### Rule 1: Slice 1 is ALWAYS the Basic Flow Alone
- **Slice 1 must implement only the Main Success Scenario (happy path), end-to-end, and nothing else.**
- Zero alternative flows in Slice 1.
- *Rationale*: Early stakeholder feedback on the working basic flow routinely changes the alternative flows before they are even built. Proving the happy path first prevents wasteful rework.

### Rule 2: Subsequent Slices Group Alternative Flows by Priority
- Slice 2, 3, etc. each take **one or a few Alternative Flows**, ordered strictly by business value:
  1. High-frequency alternatives (e.g., promo code applied, existing customer shortcut).
  2. Common business validations (e.g., loan limit exceeded, out-of-stock notification).
  3. Rare or exotic technical failures (e.g., gateway timeout, hardware jam).
- *Some flows may never be built*: A use case can deliberately remain at "sufficient flows fulfilled".
- **Aggregate First, Split When Flows Diverge**: Keep initial CRUD operations grouped in one use case (e.g., `Manage Books`). Split into standalone use cases only when alternative flows diverge with distinct access roles or deep domain rules.

### Rule 3: Slices MUST Cut Vertically (End-to-End)
- A slice is never horizontal (never "build the database schema first").
- Each slice traverses all required architectural layers (UI -> API -> DB).
- Sizing is bounded by **Test Contracts** (1–5 concrete test assertions), not file counts.

### Rule 4: Tests Carry the Truth (Test-Protected - Principle 14)
- A slice without test cases has not been properly prepared.
- Each flow in a slice must have at least one corresponding test case.
- In the AI era, tests are what make code regeneration safe: the spec states the intent, the tests enforce it, and the code is generated output.

### Rule 5: State Invariants & Failure Postconditions
- Every slice must define its entry preconditions and exit guarantees.
- For failure alternative flows, the slice must verify that the **Failure Postconditions** hold (no partial transactions, state rolled back, attempt logged).

### Rule 6: All Work is a Change to a Use Case (Principle 15)
- New features, change requests (CRs), and bug fixes are all sliced from use cases.
- There is no separate "bug-fix" command and no side-channel hotfix directly to code.
- To fix a bug: update the Use Case specification or test contract first, re-slice if necessary, and re-run the implementation loop.

## Slice Lifecycle States

Each slice moves through six deterministic states:
1. **Identified**: Slice boundary selected from the use case.
2. **Defined**: Flow path, trigger, and stop conditions mapped.
3. **Analyzed**: Impact on data and architectural components analyzed (use-case realization).
4. **Prepared**: Test cases written; slice accepted as `Approved`.
5. **Implemented**: Code and tests generated by AI in an isolated workspace.
6. **Verified**: All test cases pass; slice verified against stakeholder intent.

> **CRITICAL RULE**: AI code generation (`/implement`) must ONLY run against a slice that is in the **Approved / Prepared** state.

## Output Format: Slice Ticket Definition

When slicing a Use Case, output each slice using this standardized Markdown structure:

```markdown
### Slice [N]: [Slice Name, e.g., UC-002 Slice 01: Borrow Book Basic Flow]

- **Use Case Ref:** [UC-XXX, e.g., UC-002 Borrow Book]
- **Traceability Chain:** [FR-XXX -> UC-XXX -> Flow (Basic or A#) -> BR-XXX]
- **Flow Paths:** [Basic Flow (steps 1–9) OR Alternative Flows A1, A2]
- **Value Delivered:** [One sentence explaining the observable capability delivered]
- **Lifecycle Status:** Prepared (Approved for Implementation)
- **Preconditions Required:** [State required before slice execution]
- **Exit Guarantees:** 
  - Success: [Success Postconditions]
  - Failure: [Failure Postconditions if applicable]
- **Architectural Scope:** [List of UI, API, Service, and DB layers touched]
- **LOC Budget:** [Max +50 lines, no code-golfing]
- **Test Contracts:**
  - `TC-01`: [Trigger] -> [Expected Observable Outcome]
  - `TC-02`: [Edge condition] -> [Expected Reversal/Error]
```
